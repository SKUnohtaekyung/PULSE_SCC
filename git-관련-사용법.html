Git · GitHub 사용법

SCC 저장소(PULSE_SCC)에서 실제로 쓰는 규칙과, 그 규칙이 왜 그렇게 생겼는지를 함께 적은 문서입니다.

이 문서는 AGENTS.md, CLAUDE.md, README.md, .github/ 를 근거로 만들어졌습니다. 그 파일들이 바뀌면 이 문서도 같이 고쳐야 합니다. 자동 알림 설정은 마지막 장에 있습니다.

1. Git과 GitHub는 다른 것이다

둘을 섞어 쓰면 계속 헷갈립니다. 먼저 갈라둡니다.

　GitGitHub
정체내 컴퓨터에서 도는 버전 관리 프로그램Git 저장소를 올려두고 함께 쓰는 웹 서비스
인터넷없어도 됨있어야 함
다루는 것커밋, 브랜치, 머지이슈, PR, 리뷰, 라벨, 브랜치 보호
한마디로도구절차

커밋·브랜치·머지는 Git 개념이고, 이슈·PR·리뷰·라벨은 GitHub 개념입니다. 이 저장소의 규칙 대부분은 뒤쪽, 즉 절차에 관한 것입니다.

네 가지 기본 단어

단어뜻비유
커밋 commit변경 내용을 하나의 기록으로 저장글의 저장 지점. 언제든 그 시점으로 되돌아갈 수 있다
브랜치 branch본체를 복사해 만든 별도 작업 공간원본은 두고 사본에서 고쳐보는 것
이슈 issue무엇을 왜 할지 적는 할 일 티켓작업 전에 쓰는 글. 아직 아무것도 안 바꿨다
PR pull request바꾼 내용을 본체에 합쳐달라는 제안서작업 후에 쓰는 글. 검토를 요청한다

Pull Request라는 이름은 “내 브랜치의 변경을 당겨(pull) 가 달라는 요청(request)”이라는 뜻입니다. 핵심은 본체를 직접 고치지 않고, 사본에서 고친 뒤 검토를 받고 합친다는 것입니다.

2. 전체 흐름

이슈에서 시작해 main에 반영되기까지 여섯 단계입니다. 앞의 세 단계는 Git, 뒤의 세 단계는 GitHub에서 일어납니다.

  1. 이슈 — 할 일을 등록합니다. 아직 파일은 건드리지 않습니다.
  2. 브랜치 — main의 복사본을 뜹니다. 여기서 뭘 망가뜨려도 본체는 안전합니다.
  3. 커밋 — 사본 안에서 바꾼 내용을 저장합니다.
  4. PR — 합쳐도 되는지 물어봅니다. 변경된 줄이 색으로 표시되고 줄 단위 댓글이 가능합니다.
  5. 리뷰 — 팀원이 읽고 승인하거나 수정을 요청합니다.
  6. 머지 — 승인되면 main에 합쳐지고, 연결된 이슈는 자동으로 닫힙니다.

이슈는 “왜/무엇을”, PR은 “어떻게 했는지”입니다. 이 저장소는 둘을 1:1로 묶습니다 — 이슈 1개 = TASK 1개 = 브랜치 1개 = PR 1개 (AGENTS.md 5장·6.2절).

3. 3-way 머지

두 갈래로 갈라진 작업을 합칠 때 Git이 세 지점을 비교한다는 뜻입니다. 이름의 “3”이 그 세 지점입니다.

두 지점만 본다면 — 내 파일과 상대 파일만 비교한다면 — 같은 줄이 다르게 생겼을 때 “내가 고친 건지 상대가 고친 건지” 알 수가 없습니다. 그래서 갈라지기 전의 원본을 하나 더 봅니다.

README.md 10번째 줄이 원래 팀 5명 이었다고 하면 이렇게 판정됩니다.

상황main 쪽브랜치 쪽Git의 판단
한쪽만 고침팀 5명 그대로팀 4명브랜치가 고쳤군 → 팀 4명
반대쪽만 고침팀 4명팀 5명 그대로main이 고쳤군 → 팀 4명
양쪽 다 고침팀 4명팀 6명충돌 conflict

원본과 비교하지 않으면 1번과 2번을 구분할 수 없습니다. 3-way 머지 덕분에 대부분 자동으로 합쳐지고, 정말 양쪽이 같은 줄을 건드린 세 번째 경우에만 멈춰 섭니다.

3-way 머지는 머지의 한 종류라기보다 Git이 합칠 때 쓰는 기본 계산 방식입니다. 다음 장의 종류들은 그 계산 결과를 어떤 모양으로 역사에 남길 것인가의 차이입니다.

6. 라벨 규칙

GitHub은 기본 상태로는 아무것도 강제하지 않습니다. 이 저장소는 라벨을 두 축으로 나눠 씁니다. 하나만 붙이면 안 되고 두 축을 각각 붙입니다.

축뜻개수
type:*무엇을 바꿨나1개 이상
role:*누구의 소유 영역인가정확히 1개

role:* 이 있는 이유는 4명이 같은 파일을 동시에 고치는 사고를 막기 위해서입니다. 내 소유 영역 밖 파일을 고쳐야 하면 직접 고치지 말고 이슈로 넘기거나, 불가피하면 PR 본문에 명시하고 해당 역할을 리뷰어로 지정합니다.

이슈는 템플릿이 라벨을 자동으로 붙여주지만, PR은 안 붙여줍니다. GitHub의 PR 템플릿에는 라벨 기능이 없습니다. 만들 때 --label 로 직접 지정하고, 만든 뒤 조회해서 실제로 붙었는지 확인해야 합니다. 라벨 없는 PR은 리뷰하지 않는다는 것이 AGENTS.md 6.2절의 규칙입니다.

8. 두 방식의 차이

같은 결과를 만드는 두 가지 길이 있습니다. git branch → add → commit → merge → push 는 순수하게 Git 기능만 씁니다. GitHub 없이 내 노트북 안에서도 됩니다. 이슈+PR 방식은 같은 커밋을 만들되 앞뒤에 기록과 검토를 붙입니다.

　git merge 직접이슈 + PR
필요한 것Git만GitHub
“왜 했나” 기록없음이슈에 남음
검토없음줄 단위 코멘트 가능
되돌리기커밋 해시를 찾아야 함PR 화면의 Revert 버튼
4명 협업서로의 작업을 덮어쓸 위험라벨·소유 영역으로 분리
이 저장소에서막혀 있음유일하게 허용된 경로

마지막 줄이 핵심입니다. git merge 후 git push origin main 을 하면 GitHub이 거부합니다. 선택지가 아니라 PR이 유일한 길입니다.

9. 실전 — 처음부터 끝까지

실제로 한 사이클을 도는 명령입니다. 순서대로 그대로 쓰면 됩니다.

1) 이슈 만들기

GitHub 웹에서 New issue를 눌러 템플릿을 고르는 것이 기본입니다. 터미널에서 만들려면 폼을 건너뛰므로 본문을 직접 채웁니다.

gh issue create --title "[DOCS] 명학역 상권 수치 갱신" \
  --label "type:docs" --label "role:product" \
  --body-file - <<'BODY'
## 배경

...본문...
BODY

2) 브랜치 만들기

git switch -c docs/TASK-005-myeonghak-update

브랜치 이름은 <type>/TASK-<번호>-<짧은설명> 입니다. 앞의 type 은 라벨 표의 브랜치 접두사와 같습니다.

3) 작업하고 커밋

git add research/anyang_dong_level.md
git commit -m "docs: 명학역 일대 사업체 수를 2024년 원자료로 갱신"

커밋 메시지는 Conventional Commits 규칙입니다. <type>(<범위>): <내용> 형태이고 본문은 한국어로 씁니다.

4) 올리고 PR 만들기

git push -u origin docs/TASK-005-myeonghak-update
gh pr create --base main \
  --title "docs: 명학역 일대 사업체 수 갱신" \
  --label "type:docs" --label "role:product" \
  --body-file - <<'PRBODY'
<pull_request_template.md 구조대로 채운 본문>
PRBODY

본문은 .github/pull_request_template.md 구조를 그대로 따릅니다. 섹션을 지우지 않고, 해당 없으면 해당 없음 이라고 적습니다.

5) 라벨이 붙었는지 확인

gh pr view <번호> --json labels --jq '[.labels[].name]'

안 붙었으면 gh pr edit <번호> --add-label "type:docs" 로 보완합니다.

에디터가 열리는 형태의 명령은 쓰지 않습니다. gh pr create 를 옵션 없이 실행하면 편집기가 열리는데, 자동화 세션에서는 그대로 멈춰버립니다. 그래서 --body-file - 로 표준입력에서 본문을 받습니다.

공유 브랜치에 force push하지 않습니다. 남의 커밋을 역사에서 지워버립니다. main 은 서버에서 막혀 있지만 다른 브랜치는 막혀 있지 않습니다.

12. 이 문서를 최신 상태로 유지하는 법

이 문서는 다른 파일에서 옮겨 적은 내용으로 이루어져 있습니다. 원본이 바뀌면 여기가 조용히 틀린 문서가 됩니다. 그래서 알림 장치를 걸어뒀습니다.

자동 알림

.claude/settings.json 에 PostToolUse 훅을 걸어뒀습니다. Claude Code 세션에서 AGENTS.md, CLAUDE.md, README.md, .github/ 아래 파일을 고치면 훅이 발화해 이 문서도 확인하라고 알려줍니다.

.claude/hooks/sync-git-guide.sh   ← 판정 스크립트
.claude/settings.json             ← PostToolUse(Write|Edit) 등록

훅은 알림만 합니다. 문서를 자동으로 고치지는 않습니다. 규칙 변경이 이 문서의 어느 문장에 영향을 주는지는 사람(또는 세션)이 판단해야 하고, 자동 수정은 틀린 내용을 조용히 퍼뜨릴 위험이 더 큽니다.

이 저장소에는 jq 가 없어서 스크립트는 bash 내장 기능만 씁니다. 경로의 역슬래시를 슬래시로 바꿔 Windows와 POSIX 경로를 함께 처리합니다.

훅이 안 뜨는 것 같다면 — 훅은 Claude Code 세션 안에서만 동작합니다. GitHub 웹에서 직접 파일을 고치거나 다른 편집기로 고치면 발화하지 않습니다. 그때는 위의 “근거 파일” 표를 보고 직접 대조해야 합니다.
