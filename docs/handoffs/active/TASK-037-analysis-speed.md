## Decisions

### 어디서 시간이 가는가

변경 전 구간별 시간은 [TASK-032](TASK-032-analysis-progress-steps.md)의 2026-10-09 실행 1회 기록이다: 분석 단계 시작까지 54초, 분석 약 140초, 이미지 약 35초, 합계 230초. 분석 호출 안에서 추론과 출력이 각각 얼마인지는 그때 로그가 없어 알 수 없었다.

이 230초는 앱과 Spring을 거쳐 화면을 4초 간격으로 본 값이다. 아래 Verification의 128.6초는 Python 서비스만 직접 부른 값이라 조건이 다르다. 둘을 그대로 빼서 "몇 초 줄었다"고 읽지 않는다.

### 모델·추론 강도 비교 (2026-10-13 실측)

테스트 매장(`2080629959`)에서 수집한 같은 리뷰 120건(입력 10,210토큰)에 실제 서비스와 같은 프롬프트·출력 스키마로 조합마다 **1회씩** 호출했다. 1회씩이라 몇 초 차이는 의미가 없다.

| 모델 | 추론 강도 | 전체 | 첫 출력까지 | 출력 토큰(그중 추론) | 근거 인용 검증 |
|---|---|---|---|---|---|
| `gpt-6-astra` | 지정 안 함(응답에 `medium`으로 표시) | 115.2초 | 60.2초 | 4,974 (2,070) | 26건 중 1건 실패 |
| `gpt-6-astra` | `low` | 68.0초 | 21.0초 | 3,476 (680) | 24건 모두 통과 |
| `gpt-6.1-sol` | 지정 안 함(응답에 `medium`으로 표시) | 93.7초 | 52.2초 | 4,704 (2,030) | 20건 모두 통과 |
| `gpt-6.1-sol` | `low` | 70.0초 | 15.1초 | 2,978 (411) | 17건 모두 통과 |
| `gpt-6-luna` | `low` | 24.6초 | 5.1초 | 2,410 (172) | 24건 모두 통과 |

- **`gpt-6-astra` + `low`를 골랐다**(2026-10-13 사용자 결정). 결과물을 읽어 비교했을 때 손님 유형 3개(가족, 셀프바, 가격)와 유형별 리뷰 수(49·48·36 대 51·49·39)가 기본값과 비슷했다. 이 비교는 Agent가 결과물을 읽고 내린 판단이며 사람이 평가한 것이 아니다.
- `gpt-6-luna`는 가장 빨랐지만 같은 불만을 두 유형에 되풀이해 쓰고, 유형별 리뷰 수가 크게 나오고(셀프바 79건), 인물 묘사에 얼굴·머리 구분이 없었다. 채택하지 않았다.
- `gpt-6.1-sol`은 `low`에서는 `gpt-6-astra`보다 빠르지 않았다(70.0초 대 68.0초). 추론 강도를 지정하지 않았을 때는 21.5초 빨랐다(93.7초 대 115.2초, 1회 측정). 결과물은 `low`만 읽어 봤고 수준은 비슷했다(이것도 Agent가 읽고 내린 판단이다). 고른 조합(`low`)에서 속도 이점이 없어 모델을 바꾸지 않았다. 단가는 `gpt-6-astra`의 1/5이다(아래).
- 6회 호출 비용은 합쳐 약 0.75달러다(**계산값** — 표의 토큰 수에 아래 단가를 곱했다. 청구액은 확인하지 않았다). 쓴 단가는 2026-10-13 [모델 목록](https://developers.openai.com/api/docs/models)에서 읽은 100만 토큰당 입력/출력 값이다: `gpt-6-astra` 10/50달러, `gpt-6.1-sol` 2/10달러, `gpt-6-luna` 0.10/0.50달러. 추론 토큰은 출력 토큰에 포함된다.
- 모델 ID와 지원하는 추론 강도 값은 OpenAI 공식 문서에서 확인했다: [모델 목록](https://developers.openai.com/api/docs/models), [gpt-6-astra](https://developers.openai.com/api/docs/models/gpt-6-astra), [Reasoning 가이드](https://developers.openai.com/api/docs/guides/reasoning). `gpt-6-astra`는 `none`을 받지 않는다고 적혀 있다(직접 호출해 보지는 않았다).

### 근거 인용 검증 실패

위 6회 중 2회가 "인용은 원문 그대로" 검증에 걸렸다. `gpt-6-astra` 기본값은 떨어진 두 구절을 `...`로 이어 붙였고, `gpt-6-luna` + `none`은 "부족"을 한자로 바꿔 적었다. 이 검증에 걸리면 Spring이 작업을 다시 큐에 넣어 수집부터 다시 한다. 6회 표본이라 실제 빈도는 알 수 없다.

이번 변경은 걸렸을 때 이미지를 만들지 않고 바로 멈추게 했을 뿐이다. 다시 수집하는 것은 그대로다(Unresolved).

### 수집

아래 수집 수치 가운데 51.7초(모델 비교 때)와 36초(실제 동작 때) 말고는 측정 스크립트의 화면 출력으로만 확인했다. 출력을 파일로 남기지 않았다.

- 본문 추출 단계만 따로 재면, 같은 페이지에서 요소마다 읽는 방식은 브라우저 왕복 1,058회에 5.83초, 셀렉터마다 한 번에 읽는 방식은 왕복 18회에 0.15초였다. 두 방식이 읽은 원문 1,040건과 정리 뒤 유효 리뷰 120건의 해시가 순서까지 같았다.
- 수집 전체는 같은 날 6번 재서 18~52초였다(바꾸기 전 코드, 바꾼 코드, 계측용 변형이 섞여 있다). 네이버 응답 속도에 따라 크게 흔들려, 추출 단계 5초가 줄어든 것이 전체 시간에서 따로 보이지는 않는다.
- 이미지·글꼴·미디어 요청을 받지 않게 하면 요청 873건 중 618건이 줄었으나 이 PC에서는 시간 차이가 측정 오차 안이었다. 넣지 않았다.
- 네이버 GraphQL을 직접 호출하는 방식은 "별도 요청을 만들지 않는다"는 기존 결정([TASK-012](TASK-012-analysis-pipeline.md) 리뷰 작성일 보강)에 어긋나 검토하지 않았다.

### 그 밖

- 추론 강도는 설정값으로 두었다. 지원하는 값이 모델마다 달라 모델을 바꾸면 함께 바꿔야 할 수 있다.
- 분석기 생성자의 `reasoning_effort` 기본값은 `None`(요청에 넣지 않음)이다. 실제 서비스 경로는 항상 설정값을 넘긴다.
- ADR로 남기지 않았다.

## Unresolved

- **근거 인용 검증에 걸리면 여전히 수집부터 다시 한다.** 수집한 리뷰를 둔 채 분석 호출만 다시 하거나, 프롬프트에 "이어진 한 구절을 그대로 옮긴다"를 더하는 방법이 있으나 이번에 하지 않았다.
- `low`의 결과물 수준은 매장 1곳에서 2회(비교 측정 1회, 실제 동작 1회) 본 것이 전부다. 다른 업종·리뷰가 적은 매장에서는 보지 않았다.
- 분석 호출이 여전히 가장 길다(실제 동작에서 128.6초 중 80초). 비교 측정의 `low` 호출은 68.0초 중 첫 출력까지가 21.0초였으므로 나머지는 답을 쓰는 시간으로 본다(실제 동작에서는 이 구분을 재지 않았다). 그렇다면 더 줄이려면 호출을 유형별로 나눠 동시에 돌리거나 출력을 줄여야 한다. 이미지를 분석 출력과 겹쳐 돌리는 것도 하지 않았다.
- 이미지 3장을 동시에 요청할 때 OpenAI 계정의 분당 이미지 한도에 걸리는지는 실제 동작 1회로만 봤다. 분석 두 건이 겹치면 6장이 한꺼번에 나간다.
- 이미지 한 장이 실패해도 나머지 요청이 끝날 때까지 기다린 뒤 실패를 알린다. 전에는 실패한 장에서 멈춰 뒤 장을 요청하지 않았으나, 이제는 나머지 장의 비용도 나간다.
- 이미지 요청 스레드에는 작업 ID가 넘어가지 않는다(`ThreadPoolExecutor`는 호출 시점의 context를 복사하지 않는다). 지금은 그 스레드에서 로그를 남기지 않아 영향이 없다. 거기서 로그를 남기게 되면 `job=-`로 찍힌다.
- 추론 강도를 "보내지 않음"으로 두는 설정값이 없다. 이 인자를 받지 않는 모델로 바꾸면 설정만으로는 뺄 수 없다.
- 사용량 로그는 응답의 토큰 수 항목이 있다고 보고 읽는다. 항목이 빠진 응답이 오면 분석이 로그에서 실패한다(SDK 타입으로는 필수 항목이고, 실제 호출 1회에서는 정상이었다). 사용량이 아예 없는 응답을 다루는 갈래에는 전용 테스트가 없다.
- 결과의 `model_versions`에 추론 강도를 적지 않는다. 저장된 결과만으로는 어떤 강도로 만든 것인지 알 수 없다.
- `backend/.env.example`의 `ANALYSIS_READ_TIMEOUT` 주석("실측 4~6분")과 값(15m)을 고치지 않았다.
- 수집의 '더보기' 누르기는 고정 대기(350ms)에 기대고 있어 불러오는 리뷰 수가 실행마다 달랐다(후보 120건 또는 130건 — 120건은 화면 출력으로만 봤다). 유효 리뷰는 매번 120건이었다. 이번에 손대지 않았다.
- 비교 측정에 쓴 스크립트와 결과 원자료는 저장소에 남기지 않았다. 위 표를 다시 확인하려면 다시 재야 한다.

## Do Not Assume

- 위 시간은 모두 1회씩 잰 값이다. 네이버와 OpenAI 응답 속도에 따라 달라진다.
- `low`가 인용 검증을 늘 통과한다고 가정하지 않는다. 통과한 것은 2회다.
- `backend/.env`에 `SCC_OPENAI_ANALYSIS_REASONING_EFFORT`를 넣지 않아도 `low`로 돈다. 전처럼 돌리려면 `medium`을 넣는다.
