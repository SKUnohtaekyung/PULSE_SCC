# ADR-011 — 분석 작업 큐를 PostgreSQL 임대 방식으로 구현

## Context

분석 작업은 네이버 리뷰 수집, OpenAI 분석, 페르소나 이미지 생성을 한 번에 처리한다. 실측 소요는 200~310초이고 네이버 응답 속도에 따라 편차가 크다.

구현 초기에는 컨트롤러가 작업을 만든 직후 `@Async` 로 실행했다. 이 구조에는 다음 문제가 있었다.

- **재시작 시 작업 유실.** 처리 중 서버가 내려가면 그 작업은 `RUNNING` 으로 남고 아무도 다시 집어가지 않는다. 사용자에게는 영원히 "분석 중" 으로 보인다.
- **다중 인스턴스에서 중복 실행.** 인스턴스를 늘리면 같은 작업을 둘이 처리할 수 있다. 수집과 모델 호출에 실제 비용이 드는 작업이라 중복은 곧 비용이다.
- **재시도 정책 부재.** 일시적 수집 차단과 영구 실패를 구분하지 못했다.

TASK-012 인수인계는 이 항목을 "운영 전 내구성 큐 필요" 로 남기고 큐 방식 결정을 선결 조건으로 걸어두었다.

## Decision

**외부 메시지 브로커를 도입하지 않고 PostgreSQL 한 대에 임대(lease) 기반 큐를 구현한다.**

1. 작업 상태와 소유권은 `analysis_jobs` 테이블이 갖는다. 별도 큐 저장소를 두지 않는다.
2. 워커는 `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING id` 로 한 건씩 원자적으로 집는다.
3. 집을 때 임대 만료 시각(2분)을 찍고, 처리 중에는 30초마다 하트비트로 연장한다.
4. 임대가 만료된 `RUNNING` 작업은 워커가 죽은 것으로 보고 다시 큐에 넣는다. **재시작 복구도 같은 경로로 처리하며 별도 기동 훅을 두지 않는다.**
5. 한 작업은 최대 3회 시도한다. 재시도 가능한 실패만 큐로 되돌리고, 횟수를 다 쓰면 `ANALYSIS_TIMEOUT` 으로 마감한다.
6. 컨트롤러는 실행을 시작하지 않는다. 작업은 `QUEUED` 로 남고 폴러(기본 2초)가 집어간다.

## Reason

- **의존성을 늘리지 않는다.** 팀 4명, 15주 프로젝트다. Redis·RabbitMQ·SQS 중 무엇을 골라도 운영·배포·로컬 개발 환경이 하나씩 늘어난다. 지금 필요한 처리량은 매장당 분석 1건 수준이라 브로커의 이점이 비용을 넘지 않는다.
- **이미 PostgreSQL 이 단일 진실 원천이다.** 작업 상태가 `analysis_jobs` 에 있으므로 큐를 따로 두면 두 저장소의 상태를 맞춰야 한다. 한 테이블에서 처리하면 상태와 큐가 갈라질 여지가 없다.
- `SKIP LOCKED` 는 PostgreSQL 9.5부터의 표준 기능이고 이 용도의 정석이다. 프로젝트는 PostgreSQL 18.6 을 쓴다.
- **임대 방식은 워커 사망과 정상 종료를 구분하지 않아도 된다.** 하트비트가 끊기면 회수한다. 종료 훅에 의존하지 않으므로 프로세스가 강제 종료돼도 동작한다.

## Alternatives Considered

| 대안 | 채택하지 않은 이유 |
|---|---|
| 외부 브로커(Redis·RabbitMQ·SQS) | 운영·배포·로컬 환경이 늘어난다. 현재 처리량에 이점이 없다 |
| Spring Batch / Quartz | 스케줄 실행에 강하지만 이 문제는 긴 단일 작업의 소유권·회수다. 설정 비용 대비 이득이 적다 |
| `@Async` 유지 + 기동 시 복구 훅 | 강제 종료나 프로세스 소멸에는 훅이 돌지 않는다. 다중 인스턴스 중복도 막지 못한다 |
| `SELECT FOR UPDATE` 로 트랜잭션 내내 잠금 유지 | 작업이 수 분이라 DB 커넥션을 그동안 붙들어야 한다 |

## Consequences

**확보한 것**

- 재시작·강제 종료 후에도 작업이 자동 회수된다. 실제로 처리 중 서버를 죽이고 재기동해 70초 뒤 회수·재처리·완료를 확인했다.
- 인스턴스를 늘려도 한 작업은 한 번만 실행된다.
- 일시적 실패는 재시도되고 영구 실패는 즉시 마감된다.

**감수하는 것**

| 항목 | 내용 |
|---|---|
| 폴링 지연 | 작업 시작이 최대 폴링 주기(기본 2초)만큼 늦다. 200초 넘는 작업이라 무시할 수 있다 |
| DB 부하 | 워커마다 2초 간격 질의가 늘어난다. 부분 인덱스로 대상 행을 좁혔다 |
| 중복 실행 가능성 0 은 아니다 | 임대 만료 직후 원 워커가 되살아나면 같은 작업이 두 번 돌 수 있다. 완료 처리는 `WHERE status = 'RUNNING'` 조건이라 두 번 저장되지는 않지만, **수집·모델 호출 비용은 두 번 발생할 수 있다** |
| 정확히 한 번(exactly-once) 이 아니다 | 위와 같은 이유로 at-least-once 다. 비용이 민감해지면 임대 시간을 늘리거나 작업 단위를 쪼개야 한다 |

**재검토 시점**

- 동시 분석 요청이 인스턴스당 2건을 넘게 필요해질 때
- 분석 1건 비용이 커져 중복 실행을 허용할 수 없을 때
- 인스턴스를 여러 대로 운영하기 시작할 때

**확정 필요**

- 폴링 주기·임대 시간·재시도 횟수는 로컬 실측 기준값이다. 운영 부하를 보고 조정한다.
- 3회 실패로 마감된 작업을 사용자에게 어떻게 표현할지는 `role:product` 결정이 남아 있다.
