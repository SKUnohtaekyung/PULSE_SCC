## 1. Product Overview

**흩어진 리뷰를 손님 인사이트와 실행 가능한 마케팅·운영 제안으로 바꿔주는 AI.**

네이버 지도에 공개된 가게 리뷰를 수집·분석해 손님이 그 가게를 어떻게 경험하고 기억하는지 구조화하고, 이를 손님 유형(페르소나)과 이미지로 보여준 뒤, 검증된 마케팅 지식을 참고한 AI가 마케팅·운영 개선 방향을 제안한다.

핵심은 **거대한 경영관리 SaaS가 아니라, 이미 존재하는 리뷰 데이터를 빠르게 읽어 사장님이 이해할 수 있는 형태로 바꾸는 것**이다. **Android 앱**으로 제공하며 Google 소셜 로그인과 서비스 자체 로그인을 지원한다.

## 2. Problem

외식업 자영업자는 자기 가게 리뷰가 수십·수백 개 쌓여 있어도 그것을 다 읽고 패턴을 뽑아 행동으로 옮기지 못한다. 리뷰를 읽을 시간도, 마케팅 관점으로 해석할 훈련도 없다.

기존 방식의 한계:

- **직접 읽기** — 시간이 든다. 최근 몇 개만 보게 되고 반복 패턴은 안 보인다.
- **별점·감성분석 도구** — "부정 리뷰가 늘었다"까지는 알려줘도 *그래서 무엇을 하라*가 없다.
- **마케팅 대행** — 비용 부담이 크고 신뢰하기 어렵다.

> ⚠️ 이 문제 정의는 **아직 1차 자료로 검증되지 않았다.** 공식 통계상 외식업 소상공인의 경영애로 1위는 원재료비이고 판로개척은 하위권이다. 근거 대조는 [PROBLEM_BASELINE.md](PROBLEM_BASELINE.md) 가 정본이며, 검증 수단은 §11의 인터뷰다. **"사장님이 원한다"가 아니라 "검증할 가설"로 표현한다.**

## 3. Target User

**외식업 자영업자.** 현 단계에서 지역·세부 업종으로 더 좁히지 않는다.

| | |
|---|---|
| 상황 | 매장을 직접 운영하며 주방·홀에 서 있는 시간이 길다 |
| 동기 | 손님이 왜 오고 왜 안 오는지 알고 싶지만 리뷰를 다 읽을 여유가 없다 |
| 제약 | 마케팅 전담 인력이 없다. 복잡한 데이터를 새로 입력할 시간도 없다 |
| 디지털 숙련도 | 스마트폰·포털 사용은 하지만 분석 도구·전문 용어에는 익숙하지 않다고 가정한다 |

**적합도가 낮은 매장** — 중복·무효 리뷰를 제외한 **분석 유효 리뷰가 50건 미만인 매장**은 분석을 시작하지 않는다. 50건 이상이어도 2년보다 오래된 리뷰가 분석 대상에 포함되면 현재 매장 상태와 다를 수 있다는 우려 메시지를 표시한다.

**지역**: 제품 자체는 지역 무관이다. 안양시는 **1단계 MVP 검증 장소**일 뿐이며 제품 요구사항이 아니다.

## 4. Goals

| # | 목표 | 측정 |
|---|---|---|
| G1 | 사장님이 리뷰를 직접 다 읽지 않고도 핵심 이슈를 파악한다 | 리뷰 확인에 쓰던 시간 대비 절감 (§11) |
| G2 | 분석이 읽고 끝나지 않고 **행동 후보**까지 이어진다 | 제안 중 "해보겠다"고 답한 비율 (§11) |
| G3 | 사장님이 새로 만들 자료 없이 필수 가게 정보만으로 시작한다 | 첫 결과까지 필요한 매장 데이터 입력 항목 수 (§11) |
| G4 | 결과를 디지털에 익숙하지 않은 사장님이 이해한다 | 사용성 테스트 이해도 (§11) |

## 5. Non-Goals

**이번 MVP에서 하지 않는 것.** 기능을 벌리기보다 `리뷰 → 고객 이해 → 실행 제안` 한 줄이 실제로 유용한지 먼저 확인한다.

| 제외 항목 | 이유 |
|---|---|
| **홍보영상 생성** | MVP 범위 밖. 2026-08-23 팀 결정 |
| **인플루언서 매칭** | MVP 범위 밖. 2026-08-23 팀 결정 |
| POS 연동 | 무거운 연동이 검증을 늦춘다 |
| 원가·재고 관리 | 경영관리 SaaS가 되는 방향 |
| ERP·매출 예측 | 위와 동일 |
| **월별 변화 추적·복수 저장 이력** | 4단계(§9)로 미룬다. MVP는 계정당 저장 분석 1개만 유지한다 |
| **필수 3개 외 추가 매장 데이터 입력**(메뉴·가격·매출 등) | 필요성이 확인될 때까지 받지 않는다. MVP 분석 원자료는 네이버 공개 리뷰다 |
| 카카오맵 리뷰 수집·분석 | 1차 MVP는 네이버 리뷰만 사용한다 |
| 매출 상승 보장 | 증명할 수 없다. §7 FR-006과 §8 참조 |

> **홍보영상·인플루언서 매칭은 이전 계획에 포함돼 있었다.** MVP에서 빼기로 한 것이며, 대외 커뮤니케이션에서 범위 축소를 명시한다.

## 6. Core User Journey

```
1. 사장님이 Google 계정 또는 서비스 자체 계정으로 로그인한다
2. 로그인 직후 가게 이름, 업종, 네이버 가게 URL을 필수로 입력한다
3. 서비스가 네이버 공개 리뷰를 수집한다 — 분석을 위한 필수 가게 데이터 입력은 여기까지다
4. 분석 플랫폼·리뷰 수·수집 시점·완료 시점을 확인한다
5. 리뷰 수가 많은 상위 토픽 순서의 TOP3 포디움에서 페르소나를 선택한다
6. 선택한 페르소나의 긍정 신호 / 부정 신호 / 인식 / 우선순위와 근거 리뷰를 본다
7. 마케팅·운영 제안을 받는다 — 리뷰 사실과 검토할 행동이 먼저 표시된다
8. 저장된 분석이 없으면 첫 분석 결과를 자동 저장하고 홈에 표시한다
9. 이후 분석하기에서 새 분석을 완료하면 새 결과로 교체할지 기존 결과를 유지할지 선택한다
10. 홈에서 저장된 분석 결과를 확인하고 무엇을 해볼지 판단한다
```

**3번 이후 사장님의 추가 매장 데이터 입력은 없다.** 인증 정보는 매장 데이터 입력 항목 수에 포함하지 않는다.

로그인에 성공했어도 저장된 분석 결과가 없으면 가게 분석 흐름을 완료하기 전까지 홈과 하단 내비게이션으로 넘어가지 않는다.

> **10단계의 실행 선택 저장·추적은 제품 기능이 아니다.** 제안 중 무엇을 해볼지는 §11 M3의 인터뷰 측정 대상으로만 확인한다.

### FR-002 — 각 페르소나의 리뷰 분석이 보여줄 4가지

| 관점 | 내용 |
|---|---|
| **긍정 신호** | 반복 칭찬되는 메뉴·서비스·분위기 / 재방문 의사를 만드는 요소 / **다른 가게와 비교했을 때 손님이 가치 있다고 느끼는 지점** |
| **부정 신호** | 반복되는 불만 / 대기·맛·가격·환경 등 문제 테마 / 홍보 메시지와 실제 경험의 괴리 |
| **인식** | 어떤 가게로 기억되는가 — 이미지와 분위기 / 방문 목적과 사용 상황 / **리뷰에서 반복적으로 형성되는 브랜드 인상** |
| **우선순위** | 사장님이 먼저 볼 항목. 리뷰 전체를 읽지 않아도 되게 핵심을 압축하고, 반복 빈도가 높고 개선으로 이어질 수 있는 것부터 보여준다 |

4개 관점은 가게 전체 요약으로 따로 배치하지 않고 TOP3 포디움에서 선택한 페르소나 아래에 표시한다. 각 관점에는 대표 근거 리뷰 1~2개를 기본 노출하고 나머지는 `근거 리뷰 전체 보기`로 제공한다.

### FR-005 — AI 제안의 4레이어

| 레이어 | 역할 | 출력 예 |
|---|---|---|
| 리뷰 사실 | 실제 리뷰에서 반복된 신호 | "대기 시간이 길다는 리뷰가 반복됨" |
| AI 해석 | 그 신호가 어떤 문제·기회와 연결되는지 | "피크타임 경험이 재방문 의사에 영향을 줄 가능성" |
| 전문 지식 참고 | 마케팅 자료를 RAG로 참고 | 고객 경험·재방문·리뷰 대응 원칙 |
| 제안 | 검토 가능한 행동으로 변환 | 홍보 메시지, 리뷰 대응 방향, 운영 개선 포인트 |

**RAG의 역할은 근거 보강이지 결과 보장이 아니다.** 제안을 "확정적 컨설팅"처럼 표현하지 않는다.

### 설계 원칙

| | |
|---|---|
| A | **리뷰를 사실의 출발점으로 삼는다.** AI가 결론을 먼저 만들고 리뷰를 맞추지 않는다 |
| B | **사실과 추론을 구분한다.** 확인된 것과 해석한 것을 같은 확신도로 보여주지 않는다 |
| C | **사용자 입력을 최소화한다.** 공개 리뷰만으로 가치가 나오는지 먼저 확인한다 |
| D | **읽고 끝나게 하지 않는다.** 분석 → 페르소나 → 제안을 하나의 짧은 흐름으로 |
| E | **빠른 배포와 실제 사용 테스트를 우선한다** |

### 페르소나 취급 규칙

1. 페르소나는 **리뷰 데이터를 사람이 이해하기 쉽게 바꾸는 표현 방식**이다. 그럴듯한 캐릭터를 만드는 것이 목적이 아니다.
2. **리뷰가 말하지 않은 것을 단정하지 않는다.** 연령·성별·직업을 리뷰로 확정할 수 없다면 실제 고객 데이터처럼 표현하지 않는다.
3. 반복 빈도와 근거가 확인되는 상위 토픽 3개를 선정하고, 각 토픽에 페르소나를 1개씩 생성한다.
4. 도출된 모든 페르소나는 동일한 화풍·톤·구성 규칙을 적용해 하나의 제품 경험으로 보이게 한다.
5. 근거를 충족하는 토픽이 3개보다 적으면 근거 없는 페르소나를 채워 넣지 않는다. 도출된 유형만 포디움에 표시하고 나머지 슬롯은 비운 채 리뷰 근거 부족 메시지를 보여준다.

| 분석 기준 | 비식별화·중복·무효 리뷰 제외 후 유효 리뷰 50건 이상 |
| 오래된 리뷰 | 분석 시점 기준 2년보다 오래된 리뷰가 1건 이상 포함되면 결과가 현재 상태와 다를 수 있음을 표시한다 |
| 결과 저장 | 계정당 저장 분석은 최대 1개다. 첫 결과는 자동 저장하고 이후 새 결과 저장을 선택하면 기존 저장본을 교체한다. 기존 결과 유지를 선택하면 새 결과는 저장하지 않는다 |
| 진행 표시 | 수집·분석이 1초를 넘으면 진행 상태를 표시한다 |
| 결과 표현 | 매출 상승을 약속하는 문구를 쓰지 않는다 |

## 10. Acceptance Criteria

Agent와 Reviewer는 이 항목으로 PASS/FAIL을 판정한다.

| 요구사항 | 완료 조건 |
|---|---|
| FR-001 | 가게 지정만으로 리뷰가 수집되고, 수집 건수·수집 시점이 화면에 표시된다. 수집 실패 시 이유가 사용자 언어로 표시된다 |
| FR-002 | 포디움에서 선택한 각 페르소나 아래에 4개 관점이 모두 출력되고, 각 항목에 **근거 리뷰가 연결**된다. 근거 없는 항목이 표시되지 않는다 |
| FR-003 | 근거가 확인되는 상위 토픽 3개와 토픽별 페르소나 1개씩, 총 3개가 출력되고 각각 근거 리뷰가 연결된다. 리뷰로 확인되지 않은 인구통계(연령·성별·직업)는 단정형으로 표시되지 않는다. 유효 토픽이 3개보다 적으면 도출된 유형만 표시하고 나머지 포디움 슬롯을 비운 채 리뷰 근거 부족 메시지를 표시한다 |
| FR-004 | 도출된 모든 페르소나 이미지가 OpenAI API로 생성되고 §13에서 확정할 이미지 스타일 규칙을 따른다. 정상 결과는 3개이며 유형 부족 결과는 도출된 수만큼 생성한다. OpenAI API 키는 앱에 포함되지 않는다 |
| FR-005 | 제안마다 **리뷰 사실**과 **검토할 행동**이 기본으로 함께 보이고, AI 해석과 전문 지식은 펼쳐서 확인할 수 있다 |
| FR-006 | 화면에서 `리뷰에서 확인`과 `AI 해석`이 별도 카드·배지·제목으로 구분된다 |
| FR-007 | 지원 대상 Android 실제 기기 또는 에뮬레이터에서 가게 지정부터 결과 확인까지 전 과정을 완료할 수 있다 |
| FR-008 | Google 로그인과 서비스 자체 로그인이 각각 성공·실패·세션 복원 상태를 제공하며, 인증 실패 이유를 사용자 언어로 표시한다. 자체 계정 생성 시 이메일 형식 아이디·비밀번호·전화번호 외 사용자 정보를 필수로 요구하지 않는다 |
| FR-009 | 분석 유효 리뷰 49건 이하는 분석을 시작하지 않는다. 50건 이상이면서 2년보다 오래된 리뷰가 포함되면 결과 화면에 정확성 우려 메시지를 표시한다 |
| FR-010 | 가게 이름, 정해진 업종 1개, 유효한 네이버 가게 URL이 모두 있어야 분석을 요청할 수 있다. 셋 중 하나라도 없거나 업종 값이 허용 목록 밖이면 필드별 오류를 표시한다 |
| FR-011 | 저장 분석이 없는 계정의 첫 결과는 자동 저장되어 홈에 표시된다. 저장 분석이 있는 계정이 새 분석을 완료하면 새 결과로 교체하거나 기존 결과를 유지하는 선택을 제공하고, 최종 저장 결과는 항상 1개여야 한다 |
| FR-012 | 첫 분석을 완료하기 전에는 가게 분석 흐름을 벗어날 수 없다. 완료 후 하단 내비게이션은 `홈 → 분석하기 → 마이페이지` 순서로 이동할 수 있고 가운데 분석하기가 주요 행동으로 강조된다. 마이페이지에는 분석 완료·실패 인앱 알림, 알림 설정·서비스 정보, 로그아웃, 현재 저장 결과의 페르소나 이미지 최대 3개만 포함한다 |
| 공통 | 유효 리뷰 수가 50건 미만이면 현재 건수와 필요한 기준을 화면에 표시한다 |
| 공통 | 리뷰 수집이 진행되는 동안 **진행 상태가 화면에 표시**된다. 응답 없는 정지 화면이 아니다 |
| 공통 | 허용된 네이버 지도·플레이스 도메인 밖의 URL을 입력하면 **수집을 시도하지 않고** 사용자 언어로 거부 사유를 표시한다 |

MVP가 확인하려는 것은 **"사장님이 실제로 유용하다고 느끼는가"** 하나다.

| # | 지표 | 측정 방법 | 목표 |
|---|---|---|---|
| M1 | 로그인 후 첫 결과까지 필요한 매장 데이터 입력 항목 수 | 화면 계측 | **3개**(가게 이름, 업종, 네이버 가게 URL) |
| M2 | 리뷰 확인 시간 절감 | 사용 전후 자기보고 | TBD |
| M3 | 제안 중 "해보겠다"고 답한 비율 | 테스트 후 인터뷰 | TBD |
| M4 | 결과 이해도 | 사용성 테스트 | TBD |
| M5 | 검증 대상 매장 수 | 실제 테스트 기록 | TBD |

**TBD 목표치는 1단계 테스트 대상 수가 정해진 뒤 채운다. 추측으로 채우지 않는다.**

### 검증할 가설

| # | 가설 |
|---|---|
| H1 | 사장님이 실제로 리뷰 활용에 부담을 느끼는가 |
| H2 | 그 부담이 네이버 온서비스 AI 등 무료 서비스로 해소되지 않는가 |

| H4 | 쉬운 문장형 결과를 디지털에 익숙하지 않은 사장님이 이해하는가 |

## 12. Constraints

| 항목 | 내용 |
|---|---|
| 팀 | 4명 |
| MVP 원칙 | 최대한 얇고 빠르게. 짧은 주기로 배포해 실제 외식업자가 써보게 한다 |
| 기술 스택 | Android 앱 UI는 React, 메인 백엔드는 Spring Boot, DB는 PostgreSQL, AI 처리는 Python, 페르소나 이미지는 OpenAI API. 세부 경계는 [ADR-003](../decisions/ADR-003-application-stack.md) |
| 인증 | Google 소셜 로그인 + 서비스 자체 로그인 |
| 리뷰 수집 | 1차 MVP는 네이버 리뷰만 사용한다. 네이버 robots.txt와 이용약관의 자동 수집 위험을 인지하고 Playwright 수집을 유지한다. 근거는 [ADR-002](../decisions/ADR-002-review-collection.md), 범위 변경은 [ADR-004](../decisions/ADR-004-naver-only-review-source.md) |
| 검증 장소 | 1단계는 안양시 |

### 알려진 한계 — 사용자에게 숨기지 않는다

1. **분석 유효 리뷰가 50건 미만이면 분석하지 않는다.** 50건 이상이어도 오래된 리뷰 비중과 내용에 따라 현재 상태를 정확히 반영하지 못할 수 있다.
2. **리뷰 작성자는 전체 고객이 아니다.** 분석 결과를 "전체 손님의 실제 특성"으로 일반화하지 않는다.
3. **매출 상승을 직접 증명하는 서비스가 아니다.** MVP의 약속은 "매출을 올린다"가 아니라 **"손님 인식과 개선 포인트를 더 명확하게 만든다"** 이다.
