## 1. Product Overview

**흩어진 리뷰를 손님 인사이트와 실행 가능한 마케팅·운영 제안으로 바꿔주는 AI.**

네이버 지도·카카오맵 등에 공개된 가게 리뷰를 수집·분석해 손님이 그 가게를 어떻게 경험하고 기억하는지 구조화하고, 이를 손님 유형(페르소나)과 이미지로 보여준 뒤, 검증된 마케팅 지식을 참고한 AI가 마케팅·운영 개선 방향을 제안한다.

핵심은 **거대한 경영관리 SaaS가 아니라, 이미 존재하는 리뷰 데이터를 빠르게 읽어 사장님이 이해할 수 있는 형태로 바꾸는 것**이다. 접근성이 좋은 **웹뷰**로 제공한다.

## 2. Problem

외식업 자영업자는 자기 가게 리뷰가 수십·수백 개 쌓여 있어도 그것을 다 읽고 패턴을 뽑아 행동으로 옮기지 못한다. 리뷰를 읽을 시간도, 마케팅 관점으로 해석할 훈련도 없다.

기존 방식의 한계:

- **직접 읽기** — 시간이 든다. 최근 몇 개만 보게 되고 반복 패턴은 안 보인다.
- **별점·감성분석 도구** — "부정 리뷰가 늘었다"까지는 알려줘도 *그래서 무엇을 하라*가 없다.
- **마케팅 대행** — 비용 부담이 크고 신뢰하기 어렵다.

> ⚠️ 이 문제 정의는 **아직 1차 자료로 검증되지 않았다.** 공식 통계상 외식업 소상공인의 경영애로 1위는 원재료비이고 판로개척은 하위권이다. 근거 대조는 [PROBLEM_BASELINE.md](PROBLEM_BASELINE.md) 가 정본이며, 검증 수단은 §11의 인터뷰다. **"사장님이 원한다"가 아니라 "검증할 가설"로 표현한다.**

## 3. Target User

**외식업 자영업자.** 현 단계에서 지역·세부 업종으로 더 좁히지 않는다.

| | |
|---|---|
| 상황 | 매장을 직접 운영하며 주방·홀에 서 있는 시간이 길다 |
| 동기 | 손님이 왜 오고 왜 안 오는지 알고 싶지만 리뷰를 다 읽을 여유가 없다 |
| 제약 | 마케팅 전담 인력이 없다. 복잡한 데이터를 새로 입력할 시간도 없다 |
| 디지털 숙련도 | 스마트폰·포털 사용은 하지만 분석 도구·전문 용어에는 익숙하지 않다고 가정한다 |

**적합도가 낮은 매장** — 리뷰가 거의 없는 신규·소규모 매장은 의미 있는 패턴이 나오지 않는다. 최소 리뷰 수 기준은 **TBD**(§13-2).

**지역**: 제품 자체는 지역 무관이다. 안양시는 **1단계 MVP 검증 장소**일 뿐이며 제품 요구사항이 아니다.

## 4. Goals

| # | 목표 | 측정 |
|---|---|---|
| G1 | 사장님이 리뷰를 직접 다 읽지 않고도 핵심 이슈를 파악한다 | 리뷰 확인에 쓰던 시간 대비 절감 (§11) |
| G2 | 분석이 읽고 끝나지 않고 **행동 후보**까지 이어진다 | 제안 중 "해보겠다"고 답한 비율 (§11) |
| G3 | 사장님이 새로 만들 자료 없이 시작한다 | 첫 결과까지 필요한 사용자 입력 항목 수 (§11) |
| G4 | 결과를 디지털에 익숙하지 않은 사장님이 이해한다 | 사용성 테스트 이해도 (§11) |

## 5. Non-Goals

**이번 MVP에서 하지 않는 것.** 기능을 벌리기보다 `리뷰 → 고객 이해 → 실행 제안` 한 줄이 실제로 유용한지 먼저 확인한다.

| 제외 항목 | 이유 |
|---|---|
| **홍보영상 생성** | MVP 범위 밖. 2026-08-23 팀 결정 |
| **인플루언서 매칭** | MVP 범위 밖. 2026-08-23 팀 결정 |
| POS 연동 | 무거운 연동이 검증을 늦춘다 |
| 원가·재고 관리 | 경영관리 SaaS가 되는 방향 |
| ERP·매출 예측 | 위와 동일 |
| **월별 변화 추적·반복 사용 구조** | 4단계(§9)로 미룬다. MVP는 **1회 실행 → 결과**다 |
| **사장님의 추가 데이터 입력**(메뉴·가격·매출) | 2단계(§9)로 미룬다. MVP는 공개 리뷰만 쓴다 |
| 매출 상승 보장 | 증명할 수 없다. §7 FR-006과 §8 참조 |

> **홍보영상·인플루언서 매칭은 이전 계획에 포함돼 있었다.** MVP에서 빼기로 한 것이며, 대외 커뮤니케이션에서 범위 축소를 명시한다.

## 6. Core User Journey

```
1. 사장님이 자기 가게를 지정한다 (가게 이름 또는 지도 URL)
2. 서비스가 공개 리뷰를 수집한다 — 사장님이 입력할 것은 여기까지다
3. 리뷰 분석 결과를 본다 — 좋아하는 것 / 불편한 것 / 어떤 가게로 기억되는지 / 먼저 볼 것
4. 손님 유형(페르소나)과 이미지를 본다
5. 마케팅·운영 제안을 받는다 — 리뷰 근거가 함께 표시된다
6. 결과를 보고 무엇을 해볼지 판단한다
```

**2번 이후 사장님의 추가 입력은 없다.** 이것이 이 제품의 진입 장벽을 결정한다.

> **6단계는 제품 기능이 아니다.** 선택을 저장하거나 실행을 추적하는 기능은 MVP에 없다(§5 Non-Goals — 반복 사용 구조는 4단계).
> 6단계는 §11 M3(제안 중 "해보겠다"고 답한 비율)의 **측정 대상**이며, 인터뷰로 확인한다.

## 7. Functional Requirements

상세 화면·기능·상태·데이터·인수 기준은 [손님분석 기능명세서](requirements/GUEST_ANALYSIS_FUNCTIONAL_SPEC.md)에서 관리한다.

| ID | 요구사항 | 우선순위 | 비고 |
|---|---|---|---|
| FR-001 | 가게를 지정하면 네이버 지도·카카오맵의 공개 리뷰를 수집한다 | P0 | 수집 방식은 [ADR-002](../decisions/ADR-002-review-collection.md) |
| FR-002 | 리뷰에서 반복 패턴을 4개 관점으로 구조화해 보여준다 | P0 | 아래 상세 |
| FR-003 | 리뷰에서 관찰 가능한 범위 안에서 손님 유형(페르소나)을 도출한다 | P0 | |
| FR-004 | 페르소나를 이미지로 표현한다. 화풍·톤·구성 규칙을 서비스 전반에서 고정한다 | P1 | |
| FR-005 | 리뷰 사실 + 페르소나 + 마케팅 지식(RAG)을 참고해 마케팅·운영 제안을 만든다 | P0 | 아래 4레이어 |
| FR-006 | **리뷰에서 확인된 사실과 AI 해석을 구분해 표시한다** | P0 | 같은 확신도로 보여주지 않는다 |
| FR-007 | 결과를 웹뷰로 제공한다 | P0 | 앱 설치 없이 접근 |

### FR-002 — 리뷰 분석이 보여줄 4가지

| 관점 | 내용 |
|---|---|
| **긍정 신호** | 반복 칭찬되는 메뉴·서비스·분위기 / 재방문 의사를 만드는 요소 / **다른 가게와 비교했을 때 손님이 가치 있다고 느끼는 지점** |
| **부정 신호** | 반복되는 불만 / 대기·맛·가격·환경 등 문제 테마 / 홍보 메시지와 실제 경험의 괴리 |
| **인식** | 어떤 가게로 기억되는가 — 이미지와 분위기 / 방문 목적과 사용 상황 / **리뷰에서 반복적으로 형성되는 브랜드 인상** |
| **우선순위** | 사장님이 먼저 볼 항목. 리뷰 전체를 읽지 않아도 되게 핵심을 압축하고, 반복 빈도가 높고 개선으로 이어질 수 있는 것부터 보여준다 |

### FR-005 — AI 제안의 4레이어

| 레이어 | 역할 | 출력 예 |
|---|---|---|
| 리뷰 사실 | 실제 리뷰에서 반복된 신호 | "대기 시간이 길다는 리뷰가 반복됨" |
| AI 해석 | 그 신호가 어떤 문제·기회와 연결되는지 | "피크타임 경험이 재방문 의사에 영향을 줄 가능성" |
| 전문 지식 참고 | 마케팅 자료를 RAG로 참고 | 고객 경험·재방문·리뷰 대응 원칙 |
| 제안 | 검토 가능한 행동으로 변환 | 홍보 메시지, 리뷰 대응 방향, 운영 개선 포인트 |

**RAG의 역할은 근거 보강이지 결과 보장이 아니다.** 제안을 "확정적 컨설팅"처럼 표현하지 않는다.

### 설계 원칙

| | |
|---|---|
| A | **리뷰를 사실의 출발점으로 삼는다.** AI가 결론을 먼저 만들고 리뷰를 맞추지 않는다 |
| B | **사실과 추론을 구분한다.** 확인된 것과 해석한 것을 같은 확신도로 보여주지 않는다 |
| C | **사용자 입력을 최소화한다.** 공개 리뷰만으로 가치가 나오는지 먼저 확인한다 |
| D | **읽고 끝나게 하지 않는다.** 분석 → 페르소나 → 제안을 하나의 짧은 흐름으로 |
| E | **빠른 배포와 실제 사용 테스트를 우선한다** |

### 페르소나 취급 규칙

1. 페르소나는 **리뷰 데이터를 사람이 이해하기 쉽게 바꾸는 표현 방식**이다. 그럴듯한 캐릭터를 만드는 것이 목적이 아니다.
2. **리뷰가 말하지 않은 것을 단정하지 않는다.** 연령·성별·직업을 리뷰로 확정할 수 없다면 실제 고객 데이터처럼 표현하지 않는다.
3. 여러 페르소나가 생성돼도 화풍·톤·구성 규칙을 고정해 하나의 제품 경험으로 보이게 한다.

### 단계별 확장

| 단계 | 내용 | 조건 |
|---|---|---|
| **1** | 실제 외식업자 대상 MVP 테스트 (**안양시**에서 수행) | 지금 |

## 10. Acceptance Criteria

Agent와 Reviewer는 이 항목으로 PASS/FAIL을 판정한다.

| 요구사항 | 완료 조건 |
|---|---|
| FR-001 | 가게 지정만으로 리뷰가 수집되고, 수집 건수·수집 시점이 화면에 표시된다. 수집 실패 시 이유가 사용자 언어로 표시된다 |
| FR-002 | 4개 관점이 모두 출력되고, 각 항목에 **근거 리뷰가 연결**된다. 근거 없는 항목이 표시되지 않는다 |
| FR-003 | 손님 유형이 **1개 이상 출력**되고 각 유형에 근거 리뷰가 연결된다. 그리고 리뷰로 확인되지 않은 인구통계(연령·성별·직업)가 **단정형으로 표시되지 않는다** |
| FR-004 | 서로 다른 페르소나 이미지가 **§13-9에서 확정할 이미지 스타일 규칙**을 따른다. 규칙 확정 전에는 이 항목을 판정하지 않는다 |
| FR-005 | 제안마다 4레이어 중 최소 **리뷰 사실**과 **제안**이 함께 보인다 |
| FR-006 | 화면에서 "리뷰에서 확인된 것"과 "AI 해석"이 시각적으로 구분된다 |
| FR-007 | 모바일 브라우저에서 가로 스크롤 없이 전 과정을 완료할 수 있다 |
| 공통 | 리뷰 수가 기준 미만이면 신뢰도 한계를 화면에 표시한다 (기준 §13-2) |
| 공통 | 리뷰 수집이 진행되는 동안 **진행 상태가 화면에 표시**된다. 응답 없는 정지 화면이 아니다 |
| 공통 | 허용 도메인 밖의 URL을 입력하면 **수집을 시도하지 않고** 사용자 언어로 거부 사유를 표시한다 |

## 11. Metrics

MVP가 확인하려는 것은 **"사장님이 실제로 유용하다고 느끼는가"** 하나다.

| # | 지표 | 측정 방법 | 목표 |
|---|---|---|---|
| M1 | 첫 결과까지 필요한 사용자 입력 항목 수 | 화면 계측 | **1개**(가게 지정) |
| M2 | 리뷰 확인 시간 절감 | 사용 전후 자기보고 | TBD |
| M3 | 제안 중 "해보겠다"고 답한 비율 | 테스트 후 인터뷰 | TBD |
| M4 | 결과 이해도 | 사용성 테스트 | TBD |
| M5 | 검증 대상 매장 수 | 실제 테스트 기록 | TBD |

**TBD 목표치는 1단계 테스트 대상 수가 정해진 뒤 채운다. 추측으로 채우지 않는다.**

### 검증할 가설

| # | 가설 |
|---|---|
| H1 | 사장님이 실제로 리뷰 활용에 부담을 느끼는가 |
| H2 | 그 부담이 네이버 온서비스 AI 등 무료 서비스로 해소되지 않는가 |
| H3 | 리뷰 인사이트가 실제 운영·홍보 의사결정을 바꾸는가 |
| H4 | 쉬운 문장형 결과를 디지털에 익숙하지 않은 사장님이 이해하는가 |

## 12. Constraints

| 항목 | 내용 |
|---|---|
| 팀 | 4명 |
| MVP 원칙 | 최대한 얇고 빠르게. 짧은 주기로 배포해 실제 외식업자가 써보게 한다 |
| 기술 스택 | **미확정.** 확정 시 `docs/decisions/` 에 ADR 기록 (`AGENTS.md` 2장) |
| 리뷰 수집 | 네이버 지도·카카오맵 robots.txt는 AI·RAG 목적 봇 접근을 명시적으로 금지하고, 네이버 이용약관도 자동화 수단에 의한 수집을 금지한다. **팀은 2026-08-23에 Playwright 수집으로 진행하기로 결정했다.** 근거와 결과는 [ADR-002](../decisions/ADR-002-review-collection.md) |
| 검증 장소 | 1단계는 안양시 |

### 알려진 한계 — 사용자에게 숨기지 않는다

1. **리뷰 수가 적으면 신뢰도가 떨어진다.** 리뷰가 거의 없는 매장은 의미 있는 패턴이 나오지 않는다.
2. **리뷰 작성자는 전체 고객이 아니다.** 분석 결과를 "전체 손님의 실제 특성"으로 일반화하지 않는다.
3. **매출 상승을 직접 증명하는 서비스가 아니다.** MVP의 약속은 "매출을 올린다"가 아니라 **"손님 인식과 개선 포인트를 더 명확하게 만든다"** 이다.
