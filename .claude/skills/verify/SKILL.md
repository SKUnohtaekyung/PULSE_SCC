# verify — 코드 검증

목적: **실제로 실행한 결과만으로** 변경의 안전성을 판정한다.

## 0. 전제

`AGENTS.md` 3장의 실행 명령 표는 현재 전부 `TBD` 이고, 루트에 `package.json` 이 없다.
**따라서 명령을 추측해서 실행하지 않는다.** 아래 1단계로 실제 존재하는 명령을 먼저 찾는다.

## 1. 실행 가능한 명령 탐색

이 순서로 실제 파일을 읽어 확인한다.

1. `package.json` 의 `scripts`
2. `Makefile` / `Taskfile.yml` / `justfile`
3. `pyproject.toml`, `go.mod` 등 언어별 매니페스트
4. `.github/workflows/*` 에 이미 정의된 명령
5. `AGENTS.md` 3장 표

발견한 명령이 `AGENTS.md` 3장 표와 다르면 **표가 stale인 것이다.** 검증 후 표를 갱신한다.
어느 것도 없으면 여기서 멈추고 "실행 가능한 검증 명령이 없음"이라고 보고한다. 없는 명령을 만들어 실행하지 않는다.

## 2. 검증 실행

찾은 것만 실행한다. 없는 단계는 `없음` 으로 기록한다.

| 단계 | 확인 |
|---|---|
| install | 의존성 설치가 성공하는가 |
| lint | 경고/에러 0인가. 새로 생긴 경고가 있는가 |
| typecheck | 타입 에러 0인가 |
| unit test | 전부 통과하는가. 새 코드에 대응하는 테스트가 있는가 |
| integration test | 존재한다면 통과하는가 |
| build | 성공하는가. 새 빌드 경고가 있는가 |

## 3. Git diff 점검

```bash
git status --short
git diff main...HEAD --stat
```

확인할 것:

- 작업과 **무관한 파일 변경**이 섞이지 않았는가
- 소유 영역 밖 파일을 수정하지 않았는가 (`AGENTS.md` 5장)
- 커밋되면 안 되는 파일(`.env`, 빌드 산출물, 로컬 설정)이 포함되지 않았는가
- 삭제된 파일이 의도한 것인가

## 4. 실패 원인 분석

검증이 실패하면 **재실행부터 하지 않는다.**

1. 실패한 첫 번째 에러 메시지를 그대로 읽는다
2. 실패가 내 변경 때문인지, 원래 깨져 있었는지 확인한다 (`git stash` 후 재실행 또는 base 커밋에서 확인)
3. 원인이 확인된 후에만 **최소 범위**로 수정한다
4. 수정 후 실패했던 단계부터 재검증한다

원인을 모른 채 추측 수정을 반복하지 않는다.

## 5. 보고 형식

```
[실행함]
lint      : <명령> → PASS / FAIL (요약)
typecheck : <명령> → PASS / FAIL
test      : <명령> → N passed / M failed
build     : <명령> → PASS / FAIL

[없음]
integration test : 프로젝트에 정의되지 않음

[미실행]
<단계> : <실행하지 못한 이유>

[git diff]
무관한 변경: 있음 / 없음
소유 영역 위반: 있음 / 없음
```

**실행하지 않은 단계를 PASS로 쓰지 않는다.** `없음` 과 `미실행` 과 `PASS` 를 구분한다.
